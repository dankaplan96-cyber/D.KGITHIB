## Why the first run was on the Intel UHD 630

`2026-11-10-desktop-first-run.md` guessed a monitor cable in the motherboard's port. There is no cable: the machine is
a laptop with hybrid graphics. What was found:

1. **The NVIDIA driver was missing** until the afternoon of 10.11: the card ran as "Microsoft Basic Display Adapter"
   (Device Manager error 10), with eight other devices undriven after the Windows reinstall. Windows Update installed
   an old driver (442.23, 2020); it was then replaced with 582.78 from NVIDIA.
2. **With the driver in, Chrome still chose the Intel GPU.** On a hybrid laptop Windows sends a browser to the
   power-saving GPU unless the program has a per-app preference. Measured with a small WebGL page in an isolated
   Chrome profile: without the preference the renderer string is Intel UHD 630, with it NVIDIA GeForce GTX 1050. The
   page's own `powerPreference` request (`high-performance`, `low-power` or none) changed nothing either way.
3. **Fix:** Settings › System › Display › Graphics, "High performance" for `chrome.exe` and for the Test Lab's
   `node_modules/electron/dist/electron.exe` (the registry value `GpuPreference=2;` under
   `HKCU\Software\Microsoft\DirectX\UserGpuPreferences`). Chrome must be closed completely and reopened.
4. **Verified:** the user's own Chrome, opened from the taskbar, now shows in the game's overlay
   "NVIDIA, NVIDIA GeForce GTX 1050 (0x00001C8D) Direct3D11" at 60 fps on High, pixel ratio 1.25 (the user's photo,
   10.11; the same garden area gave 36.4 fps at pixel ratio 0.75 on the Intel GPU before the fix, not the identical
   view). `nvidia-smi` lists
   `chrome.exe` on the card.

For the game: `src/` never passes `powerPreference` to the WebGL context. On this machine and this Chrome it would
not have helped (point 2), so nothing is asked of the game for this.

The two failures, both the tool on the development build, not the game as far as I can tell:
- **cold-launch, "no errors while loading": 1 error** — the 404 for `favicon.ico` from the Test Lab's own server
  (the same favicon-only fail the laptop reports).
- **save-restart-load, "Continue is offered after the restart": false.** The save itself returned `ok`. Likely
  cause, read from the code and **not verified by a run**: `engine/server.mjs` listens on port 0, so the restart
  (`play.mjs` → `launch`) serves the game from a new port (this run: 61316, 49482, 60512, 62839 across launches). A
  new port is a new origin, so the browser profile's saved game is not visible to it. **Proposed for the cloud**
  (tool code, not changed here): keep one port per run in dev mode (pass the first server's port to the relaunch),
  and serve an empty `favicon.ico`.

## Conditions and what is not verified

- Windows was still finishing updates (TiWorker in the background, a restart pending) during all runs; the CPU was
  at 2–19 % before each run. Not rerun on a freshly restarted machine.
- One run each: no repeat, so no spread is known.
- The first Auto run is discarded: its window opened behind another program's window and Chrome throttled it to one
  frame a second (frames of 1016 ms on the first three routes). The runner now turns off
  `CalculateNativeWinOcclusion`, brings the page to the front and refuses to measure a throttled page; Medium and
  High were measured before that change and were not throttled (60 fps, pace 16.7 ms).
- The Test Lab's `launch.mjs` does not turn that feature off: a Quick Check started while another window covers
  Chrome could be throttled the same way. This Quick Check was not (59.4 fps on the street).
- Not measured: on battery; the desktop app (Electron); the Follow camera; fullscreen; temperatures over a long
  session (the card read 65–68 °C at the end of each 2–3 minute run).
- Nobody played these routes by hand in these runs.
