## The four findings
1. **The 4 s shadow-program step behind the black: not reproduced, not with a cold driver cache, not on build 562.**
   In every run the shadow programs compile in the preparation before the first route (500–550 ms) and take 0 ms
   behind the black, as in Chrome on 10.11. Then, with the user's word (12.11), the NVIDIA driver's shader cache
   (`%LOCALAPPDATA%\NVIDIA\DXCache`, 11 files, 17 MB) was emptied before each of two more runs:
   - **v82, cold driver cache and a fresh profile** (`driver-cold-auto.txt`): shadow programs 500 ms before the first
     route, 0 behind the black; street max 16.9 ms; arrival max 133 ms, behind the black. The warm run after it
     (`driver-warm-auto.txt`): 511 ms, 0 behind the black.
   - **Build 562 itself** (`e2a9d1dc`, the user's run's build, from a source checkout), cold driver cache, fresh profile
     (`build562-cold-auto.txt`): shadow programs 550 ms before the first route, 0 behind the black; Auto held High; street
     max 16.9 ms; arrival max 150 ms, behind the black.
   So neither the code (562 or v82) nor an empty driver cache gives the 4 s step in this runner. Not tried: the
   packaged app itself (installer, `app.asar`), the user's window size (1536×650), and Windows' own D3D shader cache
   (`D3DSCache`, not cleared). On 10.11 the machine was also still installing updates. **Treat it as a one-off of that
   start, unexplained.** If it comes back in the user's own play, a report from that session is the evidence to chase.
   **If the cloud wants to harden it anyway** (no measured gain here): the scene-change warm-up runs the
   whole sweep in one step (`main.js` `stepT('shadow programs', …)`). The load-time warm-up already splits it into
   `SHADOW_KINDS` ranges with a paint between them. The same split behind the black would keep a cold driver's
   compile from freezing one frame for seconds. The black would last as long, but the window keeps answering:
   Windows marks an app "not responding" after 5 s.
2. **The street's 288 ms frame with a 37 MB GC: not reproduced.** The street's longest frame in 4 runs is 17.0 ms.
3. **The 117 ms frame after the arrival's black: not reproduced.** The arrival's long frames are all behind the black
   (shadow batches 73–80 ms, draw batches 84–182 ms, geometry upload: the known PERF-ARRIVAL work). The one frame
   outside the black in 4 runs was 34 ms.
4. **The street's CPU work on High:** p50 7.6–10.7 / p95 9.4–13.0 ms against the user's 14.4 / 19.6 on build 562. Auto
   held High in all three Auto runs (the user's run dropped to Medium at 278 s for CPU pressure). The largest sections
   are submit main ~2 ms and people ~0.9–1.7 ms (176 calls). Nothing here asks for a change; it is under half the
   frame.

**No code change: there is no before/after to show.** (The driver cache refills on first use: the next start of any
D3D game on this machine compiles its shaders once.) None of the four findings appears on v82 in the app's own runtime
on this machine.
