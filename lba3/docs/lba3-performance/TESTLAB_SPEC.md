# LBA3 Test Lab — the user's specification (31.10.2026)

The user's own text, kept for the agent that builds the tool. Queued after the two running performance agents (SHADE-COST, TITLE-LOAD), next to the content work, in its own folder so it doesn't collide with game files.

Build a local desktop testing companion for the existing LBA3: The Awakening project: it launches the actual game on the user's computer, runs repeatable tests, collects evidence, identifies likely causes of problems, and supports a measured fix-and-retest workflow. Implement the tool (not a specification or manual instructions). Name: "LBA3 Test Lab". Work with the existing project and packaged Electron game; inspect the repository, build scripts, renderer, benchmark code, saves and existing automation first. English interface, short text.

1. **Interface:** Select Game · Select Project · Run Quick Check · Run Full Test · Reproduce Issue · Compare Builds · Open Report · Stop. Remember paths. Show current test, progress, elapsed time, current finding; no log flood. Runs without repeated Continue; stops safely on failure/timeout, records it, continues independent tests.
2. **Launch and control the real game:** (A) installed/packaged game, (B) development build from the repository. Isolated test profile and saves; never touch personal saves/settings. Prefer existing game APIs and supported Electron/browser automation; a small explicit test bridge in a test build where needed. Debug endpoints on localhost only; no global security disabling; don't assume the production EXE exposes debugging (a special build is identified in the report). Deterministic input replay for movement, combat, interaction, menus, camera. State injection may prepare a test but not replace the sequence under test. Record per test: real input / test API / injected state / preloaded assets.
3. **Measure:** frame-time p50/p95/p99/max, average FPS, missed refreshes, frames >33.3/50/100 ms, visible vs loading stalls, CPU sim and submit, GPU time (async timer queries), long tasks with call stacks, GC and memory trends, draw calls/GPU draws/triangles by pass, uploads, shader compiles, batch construction, shadow-cache builds and invalidations, region load/unload/reveal timing, effective resolution and quality, console errors/exceptions/crashes/unhandled promises, process CPU and memory, power source and display configuration, clocks/temperatures only if reliable. "Unavailable" when unsupported; never invent sensor readings or call a slow CPU probe confirmed throttling. No synchronous GPU readbacks; measure the tool's own overhead; tracing/video off in baseline runs unless enabled.
4. **Test suite:** cold launch to title; title to playable; first visit to each region; repeated visits; street traversal; furnished interiors; combat; magic-ball aim/throw/collision/return; sword and equipment switching; door and region transitions; dialogue and quests; save/exit/restart/load; death and respawn; pause/resume/focus loss/fullscreen; extended traversal for memory growth; opening cinematic. Only features that exist. Outcome assertions (door reaches destination, inventory kept after save/load, quest advances once, projectile terminal state, controls recover after a cinematic, no stuck black screen). Coverage matrix: Passed / Failed / Blocked / Not Tested.
5. **Cold vs steady state:** no preloading of every region before measuring normal play; separate cold entry, warm entry, sustained gameplay, transitions; report preparation separately and also test the normal path without it; moving a stall into warm-up or black is not eliminating it.
6. **Fix known measurement weaknesses:** arrival triangle/lamp counts differ between fixed and adaptive runs; empty-render pacing drifting during the suite; preset descriptions vs applied MSAA, lamps, resolution floors; Auto holding Medium below 60 (by the user's design: Medium is Auto's floor — report it as such); FPS summaries vs frame-time distributions. Identical saves, camera paths, seeds, timelines; restore settings and scene state between variants; log actual settings and visible contents; time per region and loading state; baseline → candidate → baseline; repeat ≥3×; flag unstable conditions; battery and plugged separate; consistent windows; keep raw timestamps.
7. **Evidence on problems:** bounded lightweight telemetry ring; on an error or stall past a threshold save nearby telemetry, region/position/camera/quest state/settings, a screenshot after the event, call stacks, a reproduction scenario; rerun hard cases with detailed tracing. No continuous video during performance runs. Distinguish confirmed cause / likely cause / unexplained symptom.
8. **Diagnose without blindly reducing quality:** ranked findings (player impact, frequency, cost, confidence, visual risk); areas: long callbacks, runtime batch construction, uploads after reveal, terrain/scenery shaders, edge smoothing and duplicate post, unnecessary shadow-cache rebuilds, hidden world updates, excessive submission, resource growth, Auto not responding. Preserve character design, nearby animation, world density, lighting identity, combat responsiveness; diagnostic variants restored after the test and never auto-accepted as fixes.
9. **Animation and visuals:** repeatable captures for idle, walk/run, turning, jump/landing, ball throw/release, sword attacks, damage reactions, dialogue gestures, cinematic transitions; assertions for missing clips, frozen playback, invalid transforms, T-poses, wrong release events, camera clipping, missing assets; contact sheets or short clips; issues needing visual judgment flagged separately.
10. **Claude Code:** useful without an AI subscription (run, capture, export locally). Machine-readable report and a concise Claude Code task file (finding ID, severity, repro command, evidence paths, source locations, expected vs observed, acceptance criteria). Optional "Fix and Retest" only through a supported local Claude Code integration, checked first; no typing into chat windows, no credentials; otherwise export the task bundle and the exact command/workflow.
11. **Bounded repair loop:** clean baseline; isolated branch/worktree; preserve uncommitted work; highest-impact confirmed issue; one focused fix; its repro test; regression tests; performance and visual comparison; keep only with evidence. Up to 3 attempts per issue, then record the blocker and move on. No engine rewrite, major upgrades, content deletion, releases, or changes to the installed game. No success claims without the target hardware.
12. **Reports and delivery:** concise HTML report (what works / failed / is slow / fix first / not tested), raw JSON, CSV comparison, reproduction scenarios, screenshots and optional clips, the Claude Code task file, a manifest (game version, commit, tool version, settings, hardware, power). Packaged for Windows with the project's stack where practical; short README (install, start, stop, open results). Validate the tool: launch failure, game crash, missing save, timeout, unsupported GPU timers, Stop pressed, cleanup after interruption. Start with one complete path: launch → street test → capture → report → reproduce; then expand to the remaining supported scenarios in the same work. No mock interface or design document.
